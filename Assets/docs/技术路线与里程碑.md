# 技术路线与里程碑

> 本作品（2D 类幸存者 Roguelite）的技术规划：范围取舍、分层架构、里程碑验收、刻意不做的事。
> 环境：Unity 2022.3.62f2 / **Built-in 渲染管线** / 出包目标 Windows 与 Android。
> 记录方式：这里的每条计划都标了「已核实 / 推断」，推断项不作为施工依据。
> 最后更新：2026-10-28

---

## 1. 定位与范围

**要证明的三件事**：能独立搭一套可维护的框架；能把性能问题量化（有前后对比数据，不是口头说"优化了"）；能在有限时间里砍范围、按时交付可玩的东西。

**为什么选类幸存者**：小游戏是近两年增长最明确的赛道（2026 上半年国内小游戏收入 316.57 亿元、同比 +36.01%），且这类玩法的核心循环（自动攻击 + 掉落 + 三选一成长）能用较小体量覆盖"框架 / 对象池 / 数据驱动 / 千怪同屏"这四个我想展示的技术点。

**范围上限**（超出的一律不做，见第 6 节）：
- 2D 俯视，单机
- 美术用免费素材（**用前逐项核授权**）
- 出包只做 Windows + Android（无 Mac，iOS 不碰）

## 2. 分层架构

```
表现层  UGUI(MVC) / 特效 / 音效 / 小怪批量渲染
玩法层  Player / Weapon / Enemy / Spawner / Drop / Upgrade / Meta 成长
框架层  EventBus / FSM / Pool / ResMgr(Addressables) / UIMgr / ConfigMgr(SO) / SaveMgr(Json) / Audio
工程层  编辑器拓展 / 命令行打包 / Profiler 基准 / Git
```

分层的意义在于**替换成本**：输入设备、渲染方式、资源加载方式三者互不影响。比如 M1 把输入换成新 Input System，只动了输入层，玩法层的移动逻辑一行没改。

## 4. 里程碑与验收

| 里程碑 | 验收标准 |
|---|---|
| **M1 白盒** | 能移动、自动攻击、击杀敌人、死亡重开（详见 `M1-白盒策划案.md`） |
| **M2-a 范围检查点** | 能连续玩 5 分钟不崩。**不达标就把方案砍成单一机制原型，不加时间** |
| **M2 核心循环** | 升级三选一可用；对象池生效，Profiler 里 GC Alloc 平稳 |
| **M3 内容** | 4 种武器、3 种被动、4 种敌人、1 个 Boss；天赋树；存档读写；2–3 人试玩 |
| **M4 优化与交付** | 只做四组：① 千怪同屏改造（批量渲染 + 数据导向 + 空间分区合并为一次改造，产出前后对比表）② Windows 可运行包 ③ Addressables 远程加载 + 一次不重启生效的资源更新 ④ README + 演示 GIF + demo |
| **M5 可选** | 联网 mini demo / 微信小游戏版 / 编辑器工具 / 触屏适配 |

工时是按"每周 8–10 小时"估的推断值，M1 完成后用实际工时校准一次。

**M4 为什么合并成一次改造**：批量渲染、数据导向、空间分区三项如果拆开做，每次都要重搭压测场景和基准数据；合并后一套场景、一次对比，节省的是重复搭建成本而不是实现成本。

## 5. 待验证项与 spike

以下都**未经核实**，不作为施工依据，各留约 1 小时 spike 确认：

- `RenderMeshInstanced` 在 2022.3 是否可用、单次实例数上限——不行就退回 `DrawMeshInstanced`。
- 自定义实例化 shader 在 Built-in 管线下的写法与成本（本项目已是 Built-in，不走 URP 的 HLSL 路线）。
- Addressables 异步初始化的启动耗时。
- Addressables / Input System 的具体版本以 Package Manager 里 2022.3 对应版本为准。

**三个 spike（M1 前后各约 1 小时）**：① 实例化渲染能否出图；② Addressables 异步初始化；③ 命令行 `-batchmode` 出包。

## 6. 刻意不做的事

不是"没时间做"，是**判断做它性价比低**：

| 不做 | 理由 |
|---|---|
| 联网 / 服务器 | 与"框架与性能"的证明目标无关，M5 可选一个 mini demo |
| XLua 代码热更 | 只做 M4 的 Addressables **资源**热更闭环；代码热更的收益在单机 demo 里几乎为零 |
| 帧同步 | 同上，且需要联网基础 |
| 完整 ECS / DOTS | 只读概念并做一次"struct 数组单循环"的等价改造，不上框架 |
| Shader 深挖 | 只到能写 1 个实例化 Unlit 帧动画 shader |
| 3D、Spine、SDK 接入、内购与广告、Steam 上架 | 与目标无关，上架待 demo 有反馈后再议 |
| 美术自制 | 目标是证明工程能力，自制美术会吃掉 M3 全部时间 |

**一处例外要说明**：无限滑动列表**不做进作品**，但"万级列表 <0.3s"是我简历里的既有表述，面试必问，所以要能口述"对象池 + 分帧 + 可见区域计算"的完整做法——这一条按"必须能讲清"处理，不按"要做"处理。

## 7. 缩范围信号

提前写下放弃条件，是为了避免"再给两周"式的无限延期：

- M2-a 检查点（能玩 5 分钟）不过 → 砍成单一机制原型，**不加时间**。
- M2 未达标（三选一不可用或 GC Alloc 不平稳）→ 顺延 1 周；仍不达标则砍 M4 部分项保交付。
- 连续两周投入低于 6 小时 → 先缩范围，不加时间。
- M1 到期无产出 → 这份规划整体降级重写，不留装饰。

**容易踩的两个坑**：① 框架先行——第二次需要才抽象；② M3 内容膨胀——按验收表里的数量上限，多一个都不加。

另一个刻意的安排：**M2 故意用朴素写法**（MonoBehaviour 小怪 + Physics2D），完好保留 M4 优化前的"前"数据。没有可对比的旧数据，性能优化就只能靠嘴说。

## 8. 评估岗位时我会问的问题

这套问题的共同点是：**都在问"这份工作能不能给我明确的、可验证的输入"**。

1. 每天具体做什么，写代码占比多少？
2. 团队规模与项目阶段（新立 / 在运营 / 收尾）？
3. 上一任为什么走？
4. 这个岗位的产出由谁考核，谁能给我明确需求？

第 1、4 条是同一个教训：没有策划需求、全靠自己猜的项目，做出来的东西对不对没人能判定，成长也无从谈起。
